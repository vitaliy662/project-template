# 📦 Политика версионирования

> Версия 1.0 · Принята: YYYY-MM-DD  
> Применимо ко всем компонентам проекта (код, API, CLI, документация)

---

## 🎯 Цель
Единые правила нумерации версий для прозрачной коммуникации между разработчиками, тестировщиками и пользователями.

## 📐 Формат версии
Используем **Semantic Versioning (SemVer)** — `MAJOR.MINOR.PATCH`  
Пример: `v1.4.2`

| Часть | Когда увеличивается | Примеры |
|-------|---------------------|---------|
| **MAJOR** | Ломающие изменения (breaking changes) | API, формат данных, удаление функций |
| **MINOR** | Новая функциональность без ломки | новая фича, новый эндпоинт, улучшение |
| **PATCH** | Исправления и мелкие правки | багфиксы, рефакторинг без изменения поведения |

### Дополнительные метки (pre-release)
- `-alpha.N` — ранняя стадия, нестабильно  
- `-beta.N` — функциональность готова, идёт тестирование  
- `-rc.N` — release candidate, финальная проверка  
- `+build` — метаданные сборки (не влияет на приоритет)

**Примеры:** `v1.0.0-alpha.1`, `v2.3.0-beta.2`, `v1.4.2+20250405`

## 🔄 Правила присвоения версий

1. **Каждый релиз** (тег в git) получает версию по SemVer.  
2. **Мажорная версия 0.x** — для MVP/прототипов: `0.1.0`, `0.2.0` и т.д.  
3. **Начальная разработка**: всегда `0.1.0` (до стабилизации API).  
4. **Стабилизация** — переход на `1.0.0` после публичного релиза.

### Как решить, что менять?
- **Сломали API / изменили схему БД / удалили команду** → `MAJOR+1`  
- **Добавили новую фичу без поломки** → `MINOR+1`  
- **Исправили баг, ускорили, изменили документацию** → `PATCH+1`

## 🏷️ Работа с ветками и тегами

```text
main        → стабильные версии (только релизы)
develop     → интеграция фич
feature/*   → новые фичи (ветка от develop)
hotfix/*    → срочные исправления (ветка от main)
release/*   → подготовка релиза (ветка от develop)
```

**Теги:**  
- Формат: `v<MAJOR>.<MINOR>.<PATCH>[-pre]`  
- Пример: `v1.4.2`, `v2.0.0-rc.1`

**Правила:**
- В `main` тег ставится на каждый релиз.  
- Ветки `release/*` называются по версии: `release/v1.4.0`.  
- Хотфиксы поднимают `PATCH`: `v1.4.1`.

## 📋 Чек-лист перед присвоением версии

- [ ] Обновлён `CHANGELOG.md` (все изменения добавлены)  
- [ ] Все тесты проходят (`npm test` / `pytest` / …)  
- [ ] Обновлена документация (README, спецификации)  
- [ ] Код отформатирован, нет лишних артефактов  
- [ ] Создан тег с версией (`git tag -a v1.4.2 -m "..."`)  
- [ ] Версия обновлена в `package.json`, `setup.py`, `CMakeLists.txt` и т.д.

## 🚨 Исключения и частые случаи

| Ситуация | Действие |
|----------|----------|
| Исправление опечатки в комментарии | `PATCH` (но можно не выпускать отдельную версию) |
| Добавление поля в API с дефолтом | `MINOR` |
| Удаление deprecated-функции | `MAJOR` |
| Изменение внутренней архитектуры без изменения API | `PATCH` |
| Релиз для внутреннего тестирования | `0.x.y` или `-alpha` |
